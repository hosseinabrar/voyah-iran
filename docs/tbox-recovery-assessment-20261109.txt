MPU ROUTES
BL33 identifies platform MT2735 and contains fastboot download/flash/getvar, OEM continue, reboot-recovery, NAND read/write/erase command strings. Presence of strings is not proof that commands are enabled, safe, or callable in a specific state.
Previously USB Fastboot 0e8d:201c enumerated, but getvar/reboot were not reliably completed on macOS. Physical power cycle restored ordinary Linux. No write tested.
Gate 1: controlled enter/exit Fastboot with stable read-only replies on known-good host/cable (try Windows/Linux if macOS USB stalls), record product/version/partition information where supported. Do not send generic unlock/erase/security commands.
Gate 2: demonstrate entry to that mode WITHOUT adb or working Linux, using a verified board/service method; adb reboot bootloader alone cannot prove recovery from failed Linux.
Gate 3: identify exact NAND/UBI flashing implementation and validate recovery package mapping; generic raw nandwrite/OOB copying is not an approved recipe. Preserve boot chain and device-specific NVRAM/protect.
Gate 4: actual restore/verify/cold boot rehearsal on an identical spare TBox before cross-flash. Read-only tests cannot prove writes or power-loss behavior.
If BL33/earlier boot chain cannot run, independent factory downloader/programmer is needed. No MT2735-specific working DA/auth/service recovery kit or board recovery pinout has been verified. Generic MediaTek phone tooling is not established compatible. A/B existence alone does not establish automatic rollback or entry when both slots/boot chain fail.

MCU ROUTES
Firmware source-path strings identify CYT2B9XPlatform/Cypress; physical chip/package marking still needs confirmation. Live logs report M4/M0 02-00-07 and PBL 01-00-07.
Stock upgrade_mcu exposes switchPart/getSwitchPartResult; mcu-assist offers mode normal/bt/CAN-BT/UpgradeECU/EOL and reset/status. The application contains dual-bank upgrade/CRC/synchronization log paths. These are potential recovery mechanisms, not a tested fallback.
Cached MCU package includes App at 0x10020000 plus marker at 0x100f7ffc, and UartBT at 0x10008000 plus marker at 0x1001fffc. It is NOT a full device flash dump. Current primary bootloader, persistent MCU data and actual active application equality are not established.
Gate 1: read live version and active/pending bank/status using verified read-only OEM operations; identify PBL/UartBT/application boundaries and update ordering. Do not toggle banks as a discovery operation.
Gate 2: prove the bootloader can be entered independently when the main MCU application cannot run. A command transported by Linux/vns/app firmware does not prove this independence. Establish whether bootloader CAN/UART remains reachable and how it is powered/reset.
Gate 3: identify board SWD/JTAG pads, reference voltage and supported programmer from physical documentation/markings; perform non-mutating connect/ID/access-status/readback only. Debug access depends on protection/lifecycle. Do not accept a tool's unlock or mass-erase prompt; it can destroy the backup opportunity and identity/configuration.
Gate 4: read actual current Code Flash, Work Flash and permitted configuration; compare cached App/UartBT bytes accounting for documented bank mapping. Preserve device-specific data; do not clone another vehicle's identity/security regions.
Gate 5: recovery rehearsal on matching spare hardware with original boot stages/configuration preserved. Do not overwrite UartBT/PBL while relying on them as the only recovery path.

2026-11-10 CACHED UARTBT CONTROL-FLOW AUDIT
Inspected X cached UartBT/block0.bin, base0x10008000, reset0x1000a554.
Reset configures vector table and runtime then reaches main0x1000a5c0 via
0x1000a7c0 ->0x1000a73c ->0x1000a5c0.
Main initializes subsystems, enables interrupts, passes constant0x10020000
(App base) to0x10009c54. That helper reads hardware state low2bits from
0x40201200; unless state3 it writes App base to0x40200200 and sets state3
with keyed control write. It contains no App flash checksum/vector validity
check. This is consistent with starting the other core, not a verified
jump/fallback decision by the primary bootloader.
Afterwards main copies three bytes to shared RAM, reads0x0800132c, and if
zero loops through0x1000969c and conditional0x100090b4/0x100090f2; otherwise
returns. No App-health predicate or explicit recovery-download entry has
been identified in this bounded path. Do NOT infer no recovery exists.
Cached ZIP contains App and UartBT only; separately reported PBL01-00-07
is not available as a verified binary in this backup. UartBT name alone
must not be equated to a complete primary bootloader/recovery implementation.
No established bootloader USB endpoint or MPU-to-PBL recovery protocol.
Thus remaining unknown is the primary-stage fallback/entry behavior, not
simply retaining App base. A well-formed but crashing App also differs from
an image rejected for checksum; no proven runtime boot-success rollback.
Artifacts: ../work/tbox-mcu-recovery-20261110/boot_trace.py,
boot-main.asm,boot-start-app.asm. Offline only, no firmware edits.
