Factory camera evidence — not interchangeable with Android Camera APIs
XML command IDs: 1:257 pic_dvr, 1:258 pic_roa, 1:260 pic_dms.
Corresponding atom tbox_dvrTakePicCtrl values 1/2/3 on CAN 0xA8;
channel 0, interval 2ms, count 3, pipes false, clear_count 0.
These are different layers: command ID is NOT a CAN payload value.
X names may carry _0xA8_1 / _0x105_1 suffixes. Match the actual profile.
Atom waits up to 55000ms for ivi_tspUploadSts==2. Status 2 is factory upload
success, NOT a JPEG. Do not complete our job or display an old file on this alone.
Do not map DVR/ROA/DMS to CAR_FRONT/FRONT/BACK Android Camera enums.

OEM sequencing observed in C debug binary (archive contains annotated addresses)
proc_atoms_dcvp_send_command_request -> proc_atoms_dcvp_get_wake_lock ->
queued split -> proc_atoms_split_request_handler -> proc_atoms_split_McuCheckCb.
MCU ready requires vns_mcu_is_wakeup/getRunningStatus. Otherwise wake and retry,
up to 15 checks at 2s. Preconditions/auth/command atoms follow. Register result
callback before VehicleService remoteControl; release wake ownership afterwards.
pic_* command XML has one atom, not a guessed extra ignition/power_on command.
Power state preconditions must be checked against the C/X XML. BCM authentication
failure does not establish failure of battery/HVAC/photo or all native methods.
A direct vnsRemoteControl test is not proof that this whole sequence was replicated.

Distinct media-request flow: atoms_dcvp_gdbus_cmd_media_upload_callback parses
CameraRecordReq. GetConfigBits(8) reads DID 0xf010 through diagservice read_did;
4 config bytes, little endian. This is a remote-photo feature bit, not by itself
proof of a fitted DVR or availability of all three cameras. Photo result handler
starts a separate 80s timer. Do not conflate this with the 55s atom timeout.
read_did sync response found as (ub a(y)); runtime contract/result semantics still
need verification before wiring capability. No capability invented from APK presence.

Live VT/C location repair — 2026-11-20
Device: physical H97X using H97C3630812BP / 2.2.2VTR1.9 software.
The owner confirmed VoyahTweaks shows the vehicle position. Passive OEM D-Bus
monitoring produced no NMEA/location signal during two captures (8s + 12s),
although locationd was running. This was NOT evidence of a missing GPS fix.
The factory LocationProxy::getLocInfo getter returned a current fix (<1 second
old) from shared memory. Exact VT cloud-side consumption remains untraced;
our fix uses the factory API, not a VoyahTweaks endpoint or headunit position.
libhframework SHA256 9a876f8a7fd957b87575a2866ba76ee35aed90980a9cd4aba09584df533dde3b
matches archived stock C and installed VT/C. DWARF + disassembly establish
LocationInfos size2536, flags offset0, timestamp milliseconds offset8,
latitude offset24, longitude offset40; validity bits1(time) and4(lat/lon).
The getter locks the OEM shared-memory mutex and copies the struct. The helper
only constructs LocationProxy and invokes its getter; no GNSS mode/frequency,
vehicle wake or firmware setting is changed. Execution is isolated with a3s
limit; polling5s; original fix timestamp is preserved. NMEA subscription stays.
Unknown library hashes fail closed in the helper. X getLocInfo copies3312bytes,
so its ABI MUST NOT be treated as C. X retains the existing NMEA path pending
independent verification of its shared-memory layout. No X live-test claimed.
Private evidence: parent work/remote-live-data-20261120/ (layouts, disassembly,
read-only probe, previous agent/collector binaries). No coordinates in Git.
