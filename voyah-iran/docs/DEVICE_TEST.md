# آزمون روی هدیونیت

هدف: تأیید رفتار روی فریمور واقعی؛ تست‌های JVM جایگزین این مرحله نیستند.

1. نسخهٔ فریمور و مقادیر پیش از تست را ثبت کنید:

   ```sh
   adb shell getprop ro.build.version.release
   adb shell getprop persist.sys.timezone
   adb shell settings get global auto_time_zone
   adb shell settings get global auto_time
   ```

2. APK توسعه را نصب و برنامه را باز کنید. نوار تب باید در راست بماند و چیدمان و متن فارسی راست‌به‌چپ باشند. ورود به صفحه نباید روت درخواست کند یا تنظیمی را تغییر دهد.
3. اگر property از قبل `GMT+03:30` است، چک‌باکس باید از ابتدا تیک داشته باشد.
4. چک‌باکس را روشن کنید و در صورت وجود پیام مدیر روت، اجازهٔ برنامه را بدهید. property باید `GMT+03:30`، تنظیم `auto_time_zone` برابر `0` و `auto_time` برابر مقدار اولیه باشد.
5. ساعت لانچر، نوار وضعیت، برنامه‌های باز و پشت فرمان را مقایسه کنید. ساعت داخل برنامه تنها پیش‌نمایش بر اساس property است؛ به‌تنهایی اثبات هماهنگی بقیهٔ نمایشگرها نیست.
6. تیک را بردارید. property باید دقیقاً `Asia/Tehran` شود. در دیتابیس قدیمی ممکن است ساعت تابستانی دوباره ظاهر شود؛ این مطابق رفتار مورد درخواست است.
7. برنامه را ببندید/باز کنید و هدیونیت را ریبوت کنید؛ تیک باید با property واقعی هماهنگ بماند. یک‌بار نیز آماده‌به‌کار/خواب خودرو و بازگشت شبکه را آزمایش کنید تا مشخص شود سرویس OEM مقدار را بازنویسی می‌کند یا نه.
8. تغییر منطقه زمانی از بیرون برنامه باید پس از broadcast یا بازگشت به برنامه در تیک منعکس شود.
9. با ردکردن درخواست روت، برنامه نباید موفقیت نمایش دهد. اگر روت از پیش مجاز است، این سناریو را روی دستگاه تست بررسی کنید.
10. در زمان اجرای فرمان، کلیک‌های متعدد، جابه‌جایی تب و بازسازی Activity نباید فرمان‌های هم‌زمان ایجاد کنند.
11. در عرض‌های مختلف و مقیاس فونت بزرگ، متن و دکمه باید قابل دسترسی باشند؛ هر دو ناحیهٔ صفحه و منو قابلیت اسکرول دارند.

## بازگردانی دستی

از شِل دارای دسترسی مناسب، منطقه و وضعیت خودکار ثبت‌شدهٔ پیش از تست را برگردانید. اگر فقط تهران را می‌خواهید:

```sh
adb shell su -c "setprop persist.sys.timezone Asia/Tehran"
```

روشن‌کردن دوبارهٔ تشخیص خودکار، در صورت انتخاب قبلی کاربر:

```sh
adb shell su -c "settings put global auto_time_zone 1"
```

## محدودیت‌های عمدی

- اپ در پس‌زمینه با سرویس OEM برای بازنویسی مداوم timezone رقابت نمی‌کند.
- فرمان‌ها به CAN، حالت حرکت خودرو، TBox یا MCU نوشته نمی‌شوند.
- در timeout ممکن است فرمان تا حدی اجرا شده باشد. برنامه وضعیت را دوباره می‌خواند و خطا را نگه می‌دارد؛ نتیجهٔ timeout هرگز موفقیت قطعی نیست.
- rollback برای شکست‌های عادی در خود اسکریپت وجود دارد، اما قطع ناگهانی برق یا توقف اجباری فرایند تضمین تراکنش نمی‌دهد.
